# Переезд с корпоративного гитлаба на публичный гитхаб — Implementation Plan

**Goal:** перевести репозиторий, CI и раздачу сборок с `gitlab.internal` (проект 331)
на публичный `github.com/haasson/claude-swarm-lite`, не сломав автообновление у уже
установленных копий.

**Решено пользователем 2026-07-30:** репозиторий **публичный**; историю переносим
**полностью**, но одним проходом `filter-repo` подчищаем корпоративную почту и внутренний
адрес гитлаба; переходная версия через гитлаб **нужна** (приложение стоит не только у
автора). Сам переезд пока не делаем — это план.

---

## Что на самом деле держится за гитлаб

Git — самая простая часть: `.git` весит 14 МБ, 241 коммит, 58 тегов, 5 ветвей, крупных
бинарей в истории нет, секретов тоже (`build-info.json` с токеном всегда был в
`.gitignore` и ни разу не коммитился, `glpat-` в истории не встречается).

Держится **раздача сборок**, четырьмя точками:

| Что | Где | Сейчас |
|---|---|---|
| Автообновление | `updater.js:13` | манифест из generic registry, заголовок `PRIVATE-TOKEN` |
| Голосовые модели | `main.js:1114` | тот же реестр, тот же прошитый токен |
| Выпуск релиза | `scripts/release.mjs` | `PUT` в реестр + пуш тега через `oauth2:<token>@` |
| Публикация whisper | `scripts/publish-whisper.mjs` | `PUT` в реестр |

Плюс `.gitlab-ci.yml` (валидация, сборка `.exe` через Wine, создание GitLab Release) и
блок ссылок в `README.md`, который генерирует сам `release.mjs`.

---

## Ключевое решение: чем заменить мутабельный `latest/`

Сегодня схема опирается на то, что в generic registry можно **перезаписать** путь
`…/packages/generic/apps/latest/manifest.json`, и приложение всегда читает по одному
адресу. У гитхаба есть встроенный аналог, и он лучше:

```
https://github.com/haasson/claude-swarm-lite/releases/latest/download/manifest.json
```

`releases/latest/download/…` сам разрешается в свежий **непредварительный** релиз. То есть
`manifest.json` становится обычным ассетом каждого релиза, а отдельная «версия latest»,
которую надо не забыть перезаписать, исчезает вместе с классом ошибок «выложил файлы, забыл
манифест».

**Обязательная ловушка, проверено 2026-07-30.** Этот адрес отвечает **302**
(`releases/latest/download/…` → `releases/download/v<тег>/…` → CDN). Гитлабовский реестр
на тот же запрос отдаёт **200** без редиректов — именно поэтому `httpGet`/`download` в
`updater.js` написаны без их обработки и это никогда не всплывало. Node'овский `https.get`
редиректы сам не ходит. Без этого шага обновление сломается на всех платформах сразу,
поэтому он первый в списке задач, а не «потом причешем».

**Следствие, определяющее весь порядок переезда:** установленные копии 0.21.3 и раньше
**физически не могут** ничего скачать с гитхаба — они умрут на 302. Значит переходный
`app.asar` обязан лежать на гитлабе, и «просто перенаправить манифест на гитхаб» —
не вариант. См. Task 7.

## Task 1: научить качалку ходить по редиректам

- `updater.js`: в `httpGet` и `download` — цикл по `location` при `301/302/303/307/308`,
  лимит 5 переходов, при превышении — внятная ошибка.
- Токен при переходе на другой хост **не пересылать**: заголовки в редирект на CDN тянуть
  не нужно и вредно. После Task 2 токена не останется вовсе, но правило пусть будет сразу.
- `test/updater.test.js` — случаи «редирект → 200», «цепочка длиннее лимита».

Это единственная правка, которую стоит сделать и проверить **до** всего остального: она
безопасна при живом гитлабе и снимает главный технический риск переезда.

## Task 2: выбросить прошитый токен

Публичный репозиторий означает, что ассеты релизов качаются голым URL — учётные данные в
сборке больше не нужны.

- `scripts/write-build-info.mjs`: оставить `runtimeId`, убрать `updateToken` и предупреждение
  про `UPDATE_REGISTRY_TOKEN`. Файл по-прежнему пишется — на нём держится `enabled()` в
  `updater.js:31`, то есть выключенная обновлялка в dev.
- `updater.js`: убрать параметр `token` из `httpGet`/`download` и обоих вызовов.
- `main.js`: удалить `voiceRegToken()` (строка 1124) и передачу токена в загрузку моделей.
- Заодно пропадает грабля, описанная в `.gitlab-ci.yml`: «без `UPDATE_REGISTRY_TOKEN` сборка
  уходит с выключенным автообновлением». Забыть секрет теперь просто нечего.

Токен остаётся только **для публикации** — и это `gh auth` на машине автора, в сборку он не
попадает никогда.

## Task 3: адреса

- `updater.js:13` → `…/releases/latest/download/manifest.json`.
- `main.js:1114-1115` → `whisper.json` из `releases/latest/download/`, файлы рантайма — из
  ассетов релиза-тега `whisper-<версия>`.
- `scripts/publish-whisper.mjs`: `PUT` в реестр → `gh release create whisper-<версия>` с
  файлами ассетами. Порядок сохранить в силе: **манифест последним**, иначе приложение
  увидит половину выложенного рантайма (комментарий на строке 102 объясняет, почему).
- `docs/superpowers/plans/2026-07-09-auto-update.md` и
  `docs/superpowers/specs/2026-07-09-auto-update-design.md` — внутренний адрес там тоже
  есть, но их вычистит проход `filter-repo` из Task 6, руками трогать не нужно.

## Task 4: `release.mjs` на гитхаб

- Убрать `HOST`/`PROJECT_ID`/`PKG`, заливку через `fetch(PUT)` и пуш через
  `https://oauth2:<token>@…`.
- Порядок, который не оставляет окна с битым релизом:
  1. коммит, тег, сборка `.dmg`, `strip-asar-natives`, подсчёт sha256 — как сейчас;
  2. `gh release create v<версия> --draft` с `.dmg`, `app.asar` и `manifest.json`;
  3. пуш `main` и тега (`gh` авторизуется сам, токен в командной строке не светится);
  4. CI собирает `.exe`, доливает его в **тот же** релиз и **снимает черновик**.
- Черновик до появления `.exe` — небольшое улучшение против сегодняшнего поведения: сейчас
  манифест публикуется сразу и несколько минут обещает `.exe`, которого ещё нет. Пока релиз
  черновик, `releases/latest/download/` его не видит, и обещание становится правдой ровно в
  момент, когда файл появился.
- Блок `<!--DL-->` в README: ссылки на `releases/download/v<версия>/…`, а строку
  «Ссылки ведут в приватный GitLab — нужен доступ к репозиторию» удалить — она станет
  ложью.

## Task 5: CI

- `.gitlab-ci.yml` — удалить целиком.
- `.github/workflows/build-windows.yml` — переписать под релиз: триггер по тегу `v*`,
  сборка `npm run dist:win` на настоящем `windows-latest`, `gh release upload --clobber`,
  затем `gh release edit --draft=false`.
- Уходят оба костыля, существовавшие только из-за отсутствия не-Linux раннеров: Wine и
  ручная докачка win32-бинарника `node-pty` курлом с ретраями.
- Добавить job `validate` на PR и пуш в `main`. В гитлабе там был только `node --check`
  пяти файлов — на гитхабе имеет смысл гонять весь `npm test` (25 файлов тестов), это
  бесплатно и покрывает несравнимо больше.
- `.dmg` по-прежнему собирается локально: раннеры `macos-14` есть, но подпись у нас
  осознанно ad-hoc, так что автоматизировать нечего.

## Task 6: перенос истории

Делать до переходного релиза (Task 7), но гитлабовский `origin` сохранить вторым remote —
последний релиз уходит именно туда.

- Работать на **свежем клоне**, не в рабочей копии.
- Один проход `git filter-repo`:
  - `--mailmap`: `<корпоративная почта>` → `haasson@users.noreply.github.com`
    (249 коммитов, автор один);
  - `--replace-text`: `gitlab.internal` → `github.com/haasson`, `projects/331` → путь
    гитхаба. Внутренний адрес встречается в диффах 7 коммитов и в двух документах.
- **Ловушка с 58 тегами.** Workflow триггерится на `v*`, а старые теги содержат старую
  версию workflow — `git push --tags` поставит в очередь 58 сборок Windows. Порядок:
  выключить Actions в настройках репозитория → запушить ветки и теги → включить Actions.
- Переставить `origin` рабочей копии на гитхаб; гитлабовский оставить вторым remote до
  окончательного гашения.

## Task 7: мост — переходная версия через гитлаб

Смысл: уже установленные копии спрашивают об обновлениях у гитлаба. Новую конфигурацию надо
доставить **тем механизмом, который она заменяет**.

**Переход бесшовный, и это проверено, а не предположено.** `runtimeId` =
`sha256(версия Electron | версия node-pty)`. Electron `29.4.6` и node-pty `0.13.1` стоят в
локфайле с самых первых коммитов и ни разу не поднимались, а отпечаток в опубликованном
манифесте 0.21.3 (`6a9103fd84fd…`) совпадает с локальным. Значит `decideUpdate` вернёт
`kind: 'asar'`, то есть обычную подмену `app.asar` с перезапуском — **без переустановки,
без скачивания `.dmg`/`.exe`**, ровно как любое рядовое обновление.

> **Жёсткое условие переходного релиза:** в нём нельзя поднимать Electron или node-pty.
> Любой из этих бампов меняет `runtimeId`, превращает обновление в `installer` и требует от
> каждого human-переустановки руками. Бампы — отдельным релизом, уже после переезда.

Порядок (гитхаб готовится **первым**, гитлаб получает последний релиз):

1. Правки Task 1–3 и Task 6: редиректы, снятие токена, адреса, история на гитхабе.
2. Выложить whisper на гитхаб. Обязательно до шага 4: новый код уже смотрит туда, и без
   этого у всех, кто обновится, отвалится кнопка «Включить голосовые».
3. Создать на гитхабе релиз 0.22.0 (Task 4–5) — `.dmg`, `.exe`, `app.asar`, `manifest.json`.
   Гитхабовская сторона обязана существовать **до** шага 4: иначе обновившиеся окажутся в
   лимбе, где их проверка обновлений молча получает 404, а следующего обновления они уже не
   увидят никогда.
4. Финальный акт на гитлабе: залить в реестр 0.22.0 — тот же `app.asar`, что на гитхабе,
   плюс манифест на него. Асар обязан отдаваться гитлабом: старый клиент не ходит по
   редиректам, а гитхаб на скачивание ассета отвечает 302. В `notes` этого манифеста —
   человеческий текст про переезд: это **единственный** момент, когда мы можем что-то
   сказать существующим пользователям.
5. 0.22.1 уже целиком с гитхаба — контрольная проверка цепочки «тег → CI → релиз →
   обновление в приложении».

**Гитлабовский манифест не выключаем по расписанию.** Дешевле оставить его навсегда
указывающим на 0.22.0: он работает как односторонняя калитка, и человек, открывший
приложение через три месяца, всё равно переедет сам. Срок жизни этой калитки задаём не мы —
её закрывает отзыв прошитого read-only токена или удаление проекта 331. Пока токен жив,
отставших можно не считать; когда его отзовут, любой оставшийся на 0.21.3 замерзает навсегда
и лечится только скачиванием установщика руками.

## Оценка

Task 1–5 — примерно полдня вместе с прогоном тестов. Task 6 — минут двадцать. Task 7 — один
релизный цикл; календарного ожидания не требует, потому что калитка на гитлабе остаётся
открытой и отставшие переезжают сами, когда откроют приложение.
